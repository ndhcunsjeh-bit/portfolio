## 一句话结论

工具类小页面的价值不在功能多，而在**「打开 → 点一下 → 得到结果」中间没有多余的一步**。

## 为什么做这个

我们宿舍每天晚上八点都会重复一遍同样的对话：「吃什么？」「随便。」「那你说。」就这么僵着，最后点了同一家外卖。我当时的想法很朴素：既然我们每次都选不出来，那就让一个页面替我们选。

它是我第一个"真的每天在用"的东西，也是第一个被同学主动要链接的东西。

## 原计划 vs 实际

- **功能**：计划 抽一道菜；实际 抽 + 排除 + 恢复 + 历史
- **图片**：计划 直接存原图；实际 上传即压到 900px 转 base64
- **数据**：计划 存浏览器；实际 存浏览器 + 导出 / 导入 JSON
- **部署**：计划 本地打开；实际 GitHub Pages，单文件

## 做对了

- **抽完自动进「本次已排除」。** 不加这条，第二抽大概率还是同一碗面，工具立刻失去意义。
- **全部排除后自动恢复。** 不然清单抽空，页面变成一个死页面。
- **无图兜底用菜名哈希色块。** 没照片的菜也有稳定颜色，列表不会花。
- **导出 / 导入。** 换手机时不用重新录一遍。

## 做错了

- **图片直接存原图**，第三张就超限，页面还没报错——只是静默不保存，第二天打开发现全没了。这是最难受的一种失败：不是崩，是慢慢丢。
- **色块用随机色**，刷新一次整个清单换个样，看着像坏了。
- **清空没有二次确认**，差点把自己录了半年的清单点没了。
- **没考虑空清单**，第一次打开是一片空白，没有一句「先加两道菜试试」。

## 学到了什么

**第一，先算约束，再选方案。** 浏览器给的存储配额是 5MB 左右，一张手机照片就 2MB。这个数字我在开工前完全没想过，直到数据丢了才去查。现在我写任何东西之前，会先问一句：这条数据要存多久、多大、会不会超。

**第二，静默失败比报错可怕。** 写 localStorage 超限会抛异常，但如果外面套了 try/catch 又没提示，用户看到的就是"保存成功了、其实什么都没存"。异常要么处理，要么告诉人，不能吞掉装没事。

**第三，小工具的质量在细节里。** 「排除已抽过的」「抽空了自动恢复」「没图也有颜色」——这三条都不是需求，是我自己用了一周才发现的坑。工具类产品的竞争力就是这些没人会写进需求文档的小动作。

**第四，让数据能带走。** 导出 JSON 只花了二十分钟，但它是这个项目被同学信任的原因：他们知道自己的清单不会被锁在某个网页里。凡是用户自己积累的数据，都得给一条出口。

**第五，一个功能做到天天用，比十个功能没人用强。** 我后来想给它加"按价位筛""按距离排"，加了两天就删了——加完那次，我自己都懒得用了。它的全部价值就是"点一下就好"，多一步就废了。

## 下次改

1. 涉及图片的本地应用，写入前先压缩，别等报错才想起来。
2. 任何「删除 / 清空」都要有确认，且危险的按钮默认不选中。
3. 给「空状态」写一句人话，比放一张插图有用。
4. 数据量上限写进界面（「还剩 3.2MB」），让用户心里有数。
